# ウェブアプリケーション開発ガイド

このドキュメントは、WebToolsプロジェクトのRust/Dioxusウェブアプリケーションの開発ワークフロー、テスト戦略、ベストプラクティスについて説明します。

## 1. モダンな開発プラクティス

### 1.1. 依存関係管理

- **Cargo:** すべてのRust依存関係は`Cargo.toml`を通じて管理されます。
- **NPM:** フロントエンド依存関係（Tailwind CSSなど）は`package.json`を通じて管理されます。
- **依存関係の更新:** セキュリティパッチと改善を取り込むため、依存関係を定期的に最新の安定版に更新してください。
  ```bash
  # Rust依存関係の更新
  docker compose exec web cargo update

  # NPM依存関係の更新
  docker compose exec web npm update
  ```
- **監査:** すべての依存関係に対して定期的にセキュリティ監査を実行してください。
  ```bash
  # Rust依存関係の監査
  docker compose exec web cargo audit

  # NPM依存関係の監査
  docker compose exec web npm audit
  ```

### 1.2. テスト戦略

- **ユニットテスト:** 各モジュールには対応するユニットテストが必要です。適切な場所でモックとスタブを使用してください。テスト関数名は`test_機能_条件_期待結果`の形式に従ってください。
- **コンポーネントテスト:** 各Dioxusコンポーネントの主要機能をテストし、レンダリングと状態変更の両方をカバーしてください。
- **統合テスト:** アプリケーションの異なる部分が期待通りに連携することを確認してください。
- **エンドツーエンド（E2E）テスト:** （将来の目標）PlaywrightやCypressなどのフレームワークを使用してE2Eテストを実装し、ユーザーインタラクションをシミュレートして重要なユーザーフローをテストしてください。

### 1.3. 機能開発ワークフロー

1.  **新しいブランチの作成:**
    ```bash
    git checkout -b feature/your-feature-name
    ```
2.  **機能の実装:**
    - コーディングガイドラインとプロジェクト構造に従ってください。
    - 新機能のテストを作成または更新してください。
3.  **ローカルチェックの実行:**
    ```bash
    # コードフォーマット
    docker compose exec web cargo fmt

    # コードリント
    docker compose exec web cargo clippy --fix --bin "WebTools" --allow-no-vcs

    # テスト実行
    docker compose exec web cargo test

    # アプリケーションビルド
    docker compose exec web ./bundle.sh
    ```
4.  **コミットとプッシュ:**
    ```bash
    git add .
    git commit -m "feat: Add your feature description"
    git push origin feature/your-feature-name
    ```
5.  **プルリクエストの作成:** レビューとマージのためにプルリクエストを開いてください。

## 2. 自動化とCI/CD

### 2.1. Gitフック

- （オプション）Gitフック（例：`husky`）を使用して、フォーマットやリントなどのプリコミットチェックを自動化してください。これにより、コードがコミットされる前にコード品質基準が満たされることが保証されます。

### 2.2. 継続的インテグレーション（CI）

- CIパイプライン（例：GitHub Actions）を設定して、以下を自動的に実行してください：
  - `cargo fmt --check`でフォーマットを確認
  - `cargo clippy`でコード品質を強制
  - `cargo test`ですべてのテストを実行
  - `cargo build`でアプリケーションがコンパイルされることを確認
- 現在のCI設定については、既存の`.github/workflows/web-pr-check.yml`を参照してください。

### 2.3. 継続的デプロイメント（CD）

- `main`ブランチへの正常なマージ時に、ステージングまたは本番環境にアプリケーションを自動的にデプロイするCDパイプラインを設定してください。

## 3. 包括的セキュリティガイドライン

### 3.1. セキュアコーディングプラクティス

- **入力検証:** インジェクション攻撃（XSSなど）を防ぐため、常にユーザー入力を検証・サニタイズしてください。
- **エラーハンドリング:** ユーザーには一般的なエラーメッセージを返し、詳細なエラー情報はデバッグのためにサーバーサイドでログに記録してください。エラーメッセージで機密情報を露出しないでください。
- **認証と認可:** 堅牢な認証・認可メカニズムを実装してください。ユーザー認証情報を安全に保存してください（例：ハッシュ化とソルト化）。
- **依存関係セキュリティ:** 既知の脆弱性について依存関係を定期的に監査してください（セクション1.1を参照）。

### 3.2. シークレット管理

- ソースコードにシークレット（APIキー、データベース認証情報など）を**絶対に**ハードコードしないでください。
- シークレットの管理には環境変数を使用してください。必要な変数を示すために`.env.example`ファイルをリポジトリに提供してください。

### 3.3. ウェブセキュリティヘッダー

- 一般的なウェブ脆弱性から保護するためにセキュリティヘッダーを実装してください：
  - `Content-Security-Policy`（CSP）
  - `Strict-Transport-Security`（HSTS）
  - `X-Content-Type-Options`
  - `X-Frame-Options`
  - `Referrer-Policy`
  - `Permissions-Policy`

### 3.4. Dockerセキュリティ

- **最小権限:** コンテナプロセスを非rootユーザーとして実行してください。
- **最小ベースイメージ:** Dockerコンテナには最小で安全なベースイメージを使用してください。
- **イメージスキャン:** Dockerイメージの脆弱性を定期的にスキャンしてください。

## 4. さらなる改善

- **可観測性:** アプリケーションの可観測性を向上させるため、ログ、メトリクス、トレーシングを統合してください。
- **パフォーマンス監視:** アプリケーションの速度とリソース使用量を追跡・最適化するためのパフォーマンス監視を実装してください。
- **コードカバレッジ:** コードカバレッジを追跡し、新しいコードが適切にテストされることを保証するための最小閾値を設定してください。
